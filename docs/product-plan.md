# Resona · 回响 产品方案

日期：2026-09-20。当前阶段：产品设计已确认，完整技术方案待评审。实施依据见[完整技术方案](technical-design.md)。

项目名称：**Resona**，中文意象名 **回响**。名称借用共鸣与回响的意象，表达对交互节奏的感知，不绑定 Codex 或其他单一工具。界面主标题使用 Resona，副标题为“感知每一次回响”。

项目按 MIT 许可开源，首版通过 GitHub Releases 分发 macOS 安装包；工程与发布约定见技术方案第 14 节。已选技术栈为 Tauri 2 + React / TypeScript + Rust + SQLite。

当前视觉目标：[Resona 深色双分布原型](prototypes/04-resona-dark.png)。

## 1. 产品要解决什么问题

开发者在日常使用 Codex、Claude Code 时，希望快速知道最近一次响应等了多久、当天的响应表现如何，以及较慢的体验是偶发还是反复出现。现有 SwiftBar 插件把轮次和分位数直接列成菜单，详细信息又需要打开静态 HTML 报告，阅读负担较大。

新产品是一款独立 macOS 菜单栏应用。它让用户在工作间隙用一次点击了解最近表现，在需要分析时再进入详情。展示以明确的主次关系、趋势和活动为核心，同时保留准确的指标定义。

核心体验目标：菜单栏一眼可读；展开后约三秒内能定位最近一轮的来源、模型、首次响应和端到端速度；不离开浮层即可了解当天概况。

## 2. 用户任务与界面层级

| 层级 | 用户要完成的任务 | 展示内容 | 交互 |
| --- | --- | --- | --- |
| 菜单栏 | 不打断工作地看最近一次表现 | 紧凑来源标识和最近完成轮次的首次响应，例如 `cx · 7.8s` | 点击展开；设置中可选择显示速度或两项指标 |
| 展开浮层 | 看懂最近表现及当天概况 | 最近完成轮次、时间范围、首次响应与速度双分布、少量近期活动 | 切换范围与来源，悬停看数值，进入详情 |
| 独立详情窗口 | 找出慢轮次，比较不同来源和模型 | 较长时间范围、完整趋势、模型汇总、可排序轮次列表 | 来源/模型筛选、轮次详情、排序 |
| 设置 | 管理日常使用方式 | 开机启动、菜单栏显示项、外观、数据来源目录、采集状态 | 使用系统能力配置；需要时打开目录或检查读取状态 |

本轮已将相同深色视觉语言扩展到表现概览、轮次记录与单轮详情、通用设置、数据来源设置。完整页面内容、导航和配置语义见 [页面与交互方案](pages-and-interactions.md)。

## 3. 展开浮层的信息优先级

### 第一眼：最近完成的一轮

首次响应与端到端速度并排呈现，以暖金色数字突出。来源、模型和完成时间与它们明确关联。展示值来自同一个已完成轮次，不把当天汇总与单轮数值混排成一个结果。

有正在进行的任务时，显示独立的“进行中”状态与经过时长；最后一个完成轮次仍标注“最近完成”。不把尚未完成任务的速度当成最终结果。

### 第二眼：所选范围的概况

统计区域标题为“表现概览”，提供常驻分段控件 **今天 / 24 小时 / 7 天**，默认今天。切换后，完成轮数、来源计数、两张分布图及各自分位数同时更新。标题与空状态使用所选范围，不把统计文案固定为“今天”。

| 时间选项 | 范围语义 |
| --- | --- |
| 今天 | 本地时区当天零点至当前时间 |
| 24 小时 | 当前时间向前滚动 24 小时 |
| 7 天 | 当前时间向前滚动 7 × 24 小时 |

两张图使用同一个采样截止时间。按完成时间选取范围内已完成轮次，再各自剔除缺失指标；分位数直接从有效轮次样本计算，不平均每天的分位数。范围切换保留原图直到新快照就绪，随后同步替换，避免图表与统计数字短暂对应不同范围。

顶部“最近完成”与底部“最近动态”保持全局最新记录，不受统计范围与来源筛选影响；时间窗口、来源筛选仅属于中间统计区域，位置、区域标题和分隔线明确它们的作用范围。

统计区域采用上下排列、横向全宽的 **两张分布图**，共用 cx / cc 来源图例。图例同时用形状与颜色区分来源：cx 为青绿圆点，cc 为暖金菱形。

| 图表 | 横轴 | 分位数标记 | 阅读含义 |
| --- | --- | --- | --- |
| 首次响应分布 | 首次响应耗时，单位 s | 中位数 p50、较慢端 p95 | 越靠右，等待越久 |
| 端到端速度分布 | 输出 token / 完整轮次耗时，单位 tok/s | 较慢端 p5、中位数 p50 | 越靠左，完成效率越低 |

每个点代表一个有效轮次，垂直错位只为减少遮挡，不编码额外指标。两图允许不同有效样本数，悬停显示该点来源、模型、完成时间与数值。点较多时使用保持计数的分箱表达，不能随机丢样本后把剩余点冒充完整分布。横轴独立缩放、单位清晰，分位线由同一批实际数据计算。

原深色探索图中的来源表现长表收敛为统计标题下的 cx/cc 计数与图例，为第二张图保留空间；完整模型/来源汇总在详情窗口查看。

### 第三眼：需要进一步查看的细节

最近动态采用第一张浅色探索图的行结构，转换为深色配色：左侧为圆角方形来源标识；中间第一行显示模型，第二行显示完成状态及工具标记；右侧第一行显示完成时间，第二行并排显示首次响应和端到端速度。行之间使用细分隔线，不给每行添加独立卡片。

初始浮层显示两条，使用与顶部全局最近完成一致的数据源；点击“查看更多”进入详情的轮次列表。长模型名截断后可查看全称。保留该图的排版，不沿用其中虚构的任务摘要；不采集或展示会话正文。完整会话 ID、长列表和更多维度进入详情窗口。底部保留“查看详情”按钮，设置入口放在标题栏。

### 详情与设置的内容边界

“查看详情”打开独立详情窗口，继承浮层统计范围与来源，包含表现概览和轮次记录两个页签。概览查看真实时间趋势、两项分布、按来源与模型分组的统计；记录页支持时间、来源、模型、状态和 ID 筛选，点开右侧查看单轮的开始/完成时间、总耗时、输出 token、双指标、工具标记与可复制 ID。

设置分为通用和数据来源。通用包含登录时启动、菜单栏指标、显示来源/模型、外观、默认统计范围；数据来源包含每个工具的采集开关、日志目录选择与读取检查。关闭来源保留历史，重新打开继续补采。详细默认值、失败处理和入口规则以 [页面与交互方案](pages-and-interactions.md) 为准。

## 4. 指标与展示规则

| 内容 | 产品表达 | 定义或约束 |
| --- | --- | --- |
| TTFT | 首次响应 | 延续旧项目定义：Codex 优先记录中的原生 TTFT，缺失时回退到日志事件；Claude 根据首个合格助手事件重建。详情说明来源差异 |
| TPS | 端到端速度，单位 `tok/s` | 输出 token 数 ÷ 用户提交到 Turn 完成的总时长，包含等待与工具过程 |
| 首次响应汇总 | 中位数与较慢端 p95 | 不把分位数混写成平均值 |
| 速度汇总 | 中位数与较慢端 p5 | 速度越低越慢；不得用 p95 表示最慢端 |
| 轮次 | 已完成轮次 | 中止轮次单独标识；不算入已完成轮次及性能分位数 |
| 有效样本 | 与对应指标关联 | TTFT 与 TPS 各自排除不可计算项，提示有效样本数，避免把总轮数当作两种指标共同样本数 |
| 缺失数据 | `N/A` | 不补零，不生成看似正常的图形；真实没有完成轮次时才显示 `0 轮` |
| 长时间无请求 | 图形留空并提示无请求 | 时间轴保持真实比例，不跨空档连线 |
| 来源 | `cx` 与 `cc` | 首次说明和详情显示完整工具名称；来源不能只靠颜色区分 |

不显示服务健康分数、不推断 VPN 或服务端根因，不把端到端速度改称纯生成速度。费用、剩余额度、服务状态和任务正文均不属于第一版。

原型使用明确标识的演示数据：最近一轮为 `cx / gpt-5.6-sol / 7.8s / 21.2 tok/s`；今天完成 48 轮，其中 cx 32 轮、cc 16 轮；首次响应中位数 6.4s、p95 18.2s；速度中位数 24.6 tok/s、p5 9.1 tok/s。这些数值不代表用户的真实统计。

## 5. 视觉与交互原则

- 浮层以约 500px 逻辑宽度探索双图布局，最大高度取 780px 与屏幕可用高度减去边距中的较小值。小屏中间内容滚动，标题与底部操作保持可访问；内容不溢出屏幕。
- 字体以 macOS 系统中文和西文字体为主，数字使用等宽数字特性。正文约 14–16px，关键结果使用更大字号。
- 优先用字号、留白、对齐和分隔线分组。避免卡片套卡片、整屏指标方块和传统管理后台侧栏。
- 使用深石墨底、暖白/暖金读数与克制的青绿/暖金来源色。沿用第二张探索图的无衬线字体和细分隔线；筛选采用第一张的分段结构并转为深色。不用绿灯暗示服务健康。
- 展开先显示已有数据，后台补采后原位更新。刷新不重置筛选、不闪白、不让正在阅读的区域跳动。
- 点击外部或 Escape 关闭；详情窗口打开后独立存在。键盘可访问筛选和主要动作。
- 动画只用于展开、筛选和数据更新，克制且遵循系统减少动态效果设置。
- 第一版细化已选中的深色方向，之后再适配浅色。历史三种探索只作为附录，不再作为并行候选。

## 6. 关键状态

| 状态 | 用户看到什么 | 下一步 |
| --- | --- | --- |
| 第一次启动，发现日志 | 读取本地记录的轻量进度，已有数据逐步出现 | 等待完成；不要求输入 API Key |
| 没有本地日志 | 简洁空状态，说明支持 Codex 和 Claude Code | 使用任一工具完成一轮，或选择已有日志目录 |
| 某个来源未安装 | 已有来源照常展示，设置中说明另一个来源未发现 | 无需处理 |
| 当前筛选无结果 | 明确显示当前范围没有完成轮次 | 改变范围或清除筛选 |
| 有任务进行中 | 活动状态与经过时长；最近完成结果仍可阅读 | 完成后更新 |
| 指标缺失 | 对应位置显示 `N/A`，可查看简短说明 | 不阻断其他统计 |
| 目录不可读或采集失败 | 保留最后数据，同时显示异常与最近更新时间 | 检查来源目录或读取权限 |
| 睡眠后恢复 | 保留现有画面，补采后更新 | 无需手动重启 |

## 7. 首版范围与后续空间

首版交付独立应用、菜单栏浮层、范围/来源筛选、双分布图、最近动态、详情窗口、基础设置和开机启动。模型筛选进入详情窗口，浮层保留来源筛选。

产品约定：本地统计固定存放 `~/.resona/`，仅提供打开入口；Codex 默认从 `~/.codex` 派生活跃 `sessions/` 和归档 `archived_sessions/`，两类日志统一采集，同一 thread 的多 rollout 不重复记账。

当前交付产品方案、页面交互规格与五张当前主流程高保真静态原型：菜单栏浮层、表现概览、轮次记录与单轮详情、通用设置、数据来源设置。原型用于确认信息层级和内容密度，不代表已有可点击应用或已完成 Tauri 实现；异常状态在规格中定义，尚未逐张绘制。

## 8. 契约变更与影响

| 契约 | 本阶段 | 后续实现约束与消费方动作 |
| --- | --- | --- |
| 外部接口 | 无变化；本阶段不创建接口 | Tauri commands/events 的参数、范围及错误语义在技术方案中定义；React 与 Rust 共同遵守 |
| 内部算法/协议 | 运行时无变化；产品契约明确统计范围与双分布联动 | 指标公式保持一致，身份与 token 去重按技术方案纠正；两图共享范围与截止时间，单独计算有效样本及分位数；顶部与动态不受统计筛选影响。通信版本及测试在技术方案中定义 |
| 数据库结构 | 无变化 | 新建独立 SQLite 库；完整 DDL、旧库只读导入和兼容策略见技术方案 |
| 持久化数据 | 无变化；原型仅使用演示数据 | 不读写用户的运行时数据库；固定存入 `~/.resona/`，不可配置；Codex 同时覆盖活跃与归档目录，旧偏移不导入，新旧采集器各写自己的库 |

本次文档交付不执行 DDL；实现目标的完整 DDL 见[技术方案](technical-design.md)与[建库脚本](resona-schema-v1.sql)。

## 9. 上线步骤

本阶段交付文档和图片，不部署、不安装、不更改 SwiftBar 插件，也不启动自动任务。

1. 发布前检查：本阶段检查原型中文字、信息层级、指标单位、数据示例和浮层尺寸；应用签名、公证与资源占用在实现阶段验证。
2. 部署顺序：本阶段不适用。后续按交互原型、Rust 采集与纠正口径验证、独立应用打包、迁移验收顺序推进。
3. 数据重算/backfill：本阶段不适用。后续完整回放启用来源的可读历史，旧库只读导入为待校验候选，按技术方案去重并重建。
4. 固定 Case 验收：最新完成一轮、正在进行、两个来源混合、缺失指标、空范围、长时间无请求、采集失败、睡眠唤醒；对多 rollout、归档补全与 token 去重引起的差异逐项对账，不要求旧错误数值保持不变。
5. 恢复自动任务：本阶段不适用。后续切换时停止旧 SwiftBar 采集，再启用新应用采集和按用户设置启用开机启动。
6. 观测与回滚：本阶段不适用。后续监测空闲 CPU/内存、补采耗时和数据新鲜度；保留可恢复的旧数据副本与旧插件入口，回滚时保证单一写入者。

### 原型评审边界

本轮确认视觉方向，不将生成图中的每个细节视为正式功能契约。已查看三张原图，均完整显示浮层且主要数字可读；定稿时需要处理以下生成偏差：

- 第 1 张的近期活动包含虚构任务摘要，正式产品不采集或展示正文，应替换为完成时间、模型和工具标记。图表存在当前时间之后的样本点，正式图表必须截止到当前时间。
- 第 2 张的分布点位、坐标与分位数未严格吻合，正式分布图必须由同一批样本计算；时间范围控件需补齐。标题下的实现描述应改成用户可理解的用途说明。
- 第 3 张的相对时间与顶部时钟有分钟级偏差，正式时间必须由统一时钟计算；副标题应准确表达“观察 AI 响应表现”，避免暗示记录思考或对话正文。
- 三张均需在选定方向后补齐来源筛选、空状态与进行中状态，并在真实 460px 左右逻辑宽度下检查内容密度。
